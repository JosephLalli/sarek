If you want to build a single, production-grade TR-VCF “in the style of EnsembleTR” from GangSTR + ExpansionHunter + STRling, the core idea is to (1) force all callers onto a shared locus definition, (2) map each caller’s genotype into a common internal representation, (3) perform locus matching + allele-compatibility normalization, and (4) choose a final diploid genotype per sample with an explicit scoring/tie-break policy.

EnsembleTR itself is a concrete reference implementation of this pattern: it takes TR VCFs (currently from HipSTR, GangSTR, adVNTR, and ExpansionHunter) and requires the same reference build as was used for calling; it then converts each caller’s output into a consistent internal representation, groups “mergeable” loci, identifies compatible alleles, scores candidate diploid genotypes, and emits the best genotype (plus provenance/summary fields) as a consensus TR VCF.

For your case (GangSTR + ExpansionHunter + STRling) with a shared catalog already converted into the right formats, the simplest production workflow is to treat the catalog locus ID as the primary join key (rather than trying to rediscover locus equivalence from coordinates), because EnsembleTR’s locus-merging step is mainly needed when tools were run on partially different or slightly shifted loci; your “same catalog” condition lets you make this deterministic. TRTools’ cross-caller comparison vignette makes the same assumption: comparing callsets is most straightforward when genotypers used the same set of reference TRs.

The biggest engineering step is making STRling behave like a “TR-VCF caller” in this ecosystem. STRling’s primary output is *-genotype.txt, which contains chrom/left/right/repeatunit and allele size estimates; importantly, allele1_est and allele2_est are reported as repeat units relative to the reference, and the file “reports all STR expansion loci that pass thresholds as well as any provided as input.” In practice, you implement a small adapter that converts STRling rows into TR-VCF records keyed to your catalog locus, carrying RU and END from the catalog (or from STRling if you are allowing discovery) and translating STRling’s relative repeat-size estimates into an absolute copy-number representation used in TR-VCF (e.g., REPCN/copy-number style fields), which requires knowing the reference copy number for that locus from your catalog. The adapter should also carry STRling’s evidence counts (anchored/spanning reads, depth) into FORMAT/INFO so you can build a meaningful quality score; STRling explicitly distinguishes which allele estimate is supported by spanning vs anchored evidence, and “na” has specific semantics you’ll want to treat as low-confidence/uncertain rather than a literal value.

Once all three callers are in a comparable TR-VCF-ish form, the EnsembleTR-like merge has three conceptual steps. First, locus matching: with a shared catalog, you can define “mergeable sets” as “same locus ID” (or at least same (chrom, start, end, RU)), which is effectively EnsembleTR’s “identify mergeable loci” step. Second, allele compatibility: EnsembleTR explicitly normalizes alleles into a consistent representation before scoring—if you want to be faithful to that design, you do some form of allele normalization (for example, canonicalizing to repeat copy numbers at the catalog locus, or reconstructing allele sequences by padding/trimming against the reference interval). The EnsembleTR paper’s overview emphasizes this “compatible alleles” step before scoring genotypes. Third, genotype selection: implement a per-sample scoring rule that chooses among candidate diploid genotypes supported by one or more callers. EnsembleTR describes this as a “voting-based scheme” that scores possible diploid genotypes and outputs the best genotype and its score.

To match your stated intent (“STRling as tool-of-last-resort”), the scoring/tie-break policy should be explicit and simple: “prefer EH when present and high quality; otherwise fall back to GangSTR; otherwise fall back to STRling if it has sufficient evidence.” This is philosophically aligned with EnsembleTR’s notion of caller-specific genotype quality feeding a consensus decision (even though EnsembleTR’s exact quality model is more detailed and includes additional callers). Practically, you define (a) what counts as “present” (non-missing genotype, locus not filtered), (b) minimum caller-specific QC thresholds, and (c) a deterministic tie-break order. STRling’s output fields give you natural knobs for a “last resort” quality function (e.g., require some minimum anchored/spanning evidence and penalize na patterns), while EH and GangSTR already emit standard VCF genotype-quality style fields you can use directly.

Finally, emit a TR-VCF that is transparent about provenance. EnsembleTR’s tooling and docs emphasize that the final VCF is a consensus set of genotypes and (in their implementation) includes method/provenance information in the output. For your implementation, that usually means tagging each locus/sample call with which caller “won” (EH/GangSTR/STRling) and optionally storing the losing callers’ copy-number estimates and qualities in auxiliary FORMAT fields. This makes debugging much easier, and it also lets downstream users decide whether they want to trust “STRling-only” genotypes or treat them as candidates.

That’s the overall design: treat EH+GangSTR as first-class TR-VCF inputs, convert STRling into a compatible per-locus genotype representation using the shared catalog’s reference copy number, then implement an EnsembleTR-like locus join + allele normalization + genotype scoring, with an explicit priority order that only allows STRling to fill in when the other callers are missing or fail QC.
